# Целевое развёртывание: Windows-only

## Решение пользователя

Сервер BuildSystem и агенты развёртываются на Windows. Поддержка Linux/Unix hosting и systemd Worker не входит в текущий scope. Переносимые .NET-библиотеки и Linux CI сохраняются: это дополнительная проверка, а не обязательство поддерживать Linux deployment. Искусственный запрет запуска API вне Windows не добавляется.

Windows Server 2022 — исходный ориентир, не утверждённая фактическая конфигурация. Версия SQL Server и совместимость 1С определяются по паспорту стенда. SQL CI в Linux-контейнере проверяет SQL-сценарии, но не заменяет целевой Windows-стенд.

## Совместное развёртывание

Развёртывание выполняем пошагово с помощью ассистента: подготовка команд и конфигурации под предоставленные версии, проверка результатов без секретов, диагностика ошибок. Доступ к Windows не подразумевается автоматически; без согласованного удалённого инструмента пользователь выполняет команды на стенде и передаёт обезличенные результаты. Пароли, приватные ключи и agent tokens не присылать в чат.

Сначала поднимаем текущий API и диагностический агент. Это не приёмка MVP: UI, archive providers и реальный restore ещё не завершены.

## Что потребуется до начала

- Версия/редакция Windows Server, отдельная VM или существующий сервер.
- Где находятся API, SQL Server метаданных, Windows-агент и кластер 1С: один или несколько хостов.
- Версии/редакции SQL Server и платформы 1С; доступность .NET 10 runtime/Hosting Bundle и корпоративные ограничения установки.
- DNS-имя сервера, HTTPS-сертификат и выбранная схема hosting (IIS с ASP.NET Core Hosting Bundle либо отдельная Windows-служба после подготовки service hosting).
- Учётные записи служб, права каталогов, сетевых ресурсов и SQL. Agent DPAPI CurrentUser привязан к учётной записи, под которой импортирован credential; импорт и служба должны использовать согласованный профиль/identity.
- Разрешённые сетевые связи и firewall: пользователи/агенты → HTTPS API; API → SQL метаданных; агент/SQL → необходимые источники архивов согласно будущим providers. Не открывать SQL или 1С в интернет ради теста.
- Пути конфигурации, данных/журнала, сертификатов и логов, правила резервного копирования.

## Порядок проверки

1. Снять паспорт стенда и выбрать схему размещения. Не устанавливать компоненты и не менять firewall вслепую.
2. Собрать/publish согласованный коммит, проверить версии runtime и доступные артефакты.
3. Подготовить отдельную БД метаданных и least-privilege service identity. Применить проверенные миграции к согласованной БД, не к базе 1С; сначала резервная копия существующих данных.
4. Настроить API hosting/HTTPS, connection string через защищённую конфигурацию, доступы и персистентное защищённое хранилище Data Protection keys для cookie. Проверить authentication/roles/CSRF.
5. Подготовить каталог агента с ACL, credential под identity службы, установить Windows-службу и проверить enrollment/approval/probe/heartbeat/restart. DPAPI roundtrip и SCM lifecycle требуют реального Windows-прогона.
6. Проверить обновление, откат, резервное копирование и логи без раскрытия секретов.
7. После завершения providers отдельно принимать реальные .dt/.bak восстановления только в новые тестовые базы с reconciliation, без воздействия на рабочие ИБ.

Это план подготовки, не готовый production-install скрипт и не отчёт об уже выполненном развёртывании. Точные команды выдаются после уточнения стенда.
