# Безопасность, ошибки и восстановление

## Последовательность обновления существующей базы
Preflight -> Artifact Verification -> Backup -> Backup Verification -> Lock New Sessions -> Quiesce Existing Sessions -> LoadCfg -> UpdateDBCfg -> Verify -> Unlock (только при безопасном состоянии).

Полная загрузка CF — потенциально разрушающая операция. Перед запуском проверяются права пользователя, допустимость целевой базы (MVP: только тестовые), отсутствие активного изменяющего задания, совместимость конфигурации, целостность артефакта, доступность backup. Изменения базы вне Git требуют явного решения.

## Критичные сценарии
- Ошибка backup: остановить pipeline до загрузки CF.
- Ошибка LoadCfg/UpdateDBCfg: состояние NeedsAttention, никакого слепого retry.
- Потеря связи с агентом: lease истёк, но процесс мог продолжать работу; сверить состояние до новой выдачи.
- Неуспешная проверка после развёртывания: оставить базу в MaintenanceRequired и не снимать блокировку.
- Ошибка cleanup: задание reconciliation, уведомление оператора.

## SQL
BACKUP DATABASE и RESTORE VERIFYONLY исполняются на SQL Server, путь резервной копии относится к серверу СУБД. VERIFYONLY не заменяет тестовое восстановление. Автоматический SQL RESTORE поверх существующей базы для отката развёртывания в MVP не предусмотрен. Для заказа новой тестовой базы разрешено восстановление опубликованного шаблона либо разрешённого дискового .bak в новую БД — по правилам ниже.

## Защита
Секреты вне YAML, аргументов в логах и outputs; HTTPS, авторизация пользователей и агентов, allowlist операций CLI, проверка всех путей, аудит всех изменений, отдельные сервисные учётные записи с минимальными правами.

## Создание и удаление личных тестовых баз
RESTORE разрешён только в выделенном тестовом пуле, из опубликованной версии шаблона или проверенной фиксированной копии дискового .bak в новую зарезервированную БД. Запрещены WITH REPLACE, перезапись существующих файлов и восстановление в существующую ИБ. Пользователь не передаёт SQL, пути и произвольный адрес сервера. Шаблон публикуется администратором после проверки допустимости данных, совместимости и политики подготовки.

До первого запуска прикладного кода обеспечивается сетевая изоляция от рабочих интеграций и запрет регламентных заданий. Затем применяется обязательный профиль подготовки: тестовые адреса/учётные записи, отключение обменов, отправки писем и иных внешних действий, обработка данных и пользователей по политике шаблона. Если профиль не применён или проверка неуспешна, доступа и состояния Ready нет. Старые производственные учётные записи из backup не должны давать доступ к копии.

При сбое/отмене выполняется сверка созданных объектов. Удаление допустимо только для ресурсов с подтверждённой принадлежностью данной ReservationId/EnvironmentId; совпадение имени недостаточно. При сомнении — NeedsAttention, блокировка повторных операций и ручное решение. Неизвестный исход RESTORE или загрузки .dt нельзя автоматически повторять или компенсировать удалением, пока старый процесс не завершён и состояние не установлено.

Удаление — отдельное идемпотентное задание с авторизацией владельца или администратора и эксклюзивной блокировкой окружения/ИБ. Оно проверяет отсутствие выполняющихся изменяющих операций, закрывает доступ, завершает сеансы по политике, удаляет регистрацию ИБ и принадлежащую ей SQL БД. Квота освобождается после проверки отсутствия обоих ресурсов. Истечение пользовательского срока не отменяет lease активного задания и не разрешает конкурирующий DROP.

## Источники на диске
Дисковый архив не требует индивидуальной публикации шаблона, но наследует ACL и обязательный профиль подготовки разрешённого root. Прямые пользовательские пути, выход за root через .., symlink/junction/reparse point и подмена файла между проверкой и чтением запрещены. Контроль выполняется на хосте агента по конечному объекту, включая сетевые пути; недостаточно проверить строковый префикс. Исходный файл не меняется и не удаляется системой.

.dt загружается только в новую принадлежащую заявке ИБ без пользовательских сеансов и с закрытым прикладным доступом. Во время загрузки и до подготовки сохраняются сетевые ограничения и блокировка регламентных заданий. При невозможности гарантировать изоляцию на целевой версии сценарий останавливается. .bak использует правила RESTORE без REPLACE. Неподдерживаемые, повреждённые или изменённые архивы отклоняются; упаковки ZIP/7z не распаковываются неявно. Управление временными копиями не затрагивает исходный каталог; активный артефакт удерживается до завершения задания/reconciliation.
