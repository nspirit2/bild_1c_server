# Ответы реализатору и порядок приёмки

Дата: 22.10.2026. Нумерация соответствует 39 вопросам реализатора.

Этот документ уточняет порядок реализации и неоднозначные места исходной спецификации. Требования пользователя: самостоятельный заказ личных тестовых баз и обязательное восстановление архивов с диска в MVP. Остальные решения ниже — базовые проектные решения для начала разработки; это не сведения об уже существующей инфраструктуре и не подтверждение её готовности. Реализатор может предложить обоснованное изменение через ADR в pull request. Обычные внутренние технические решения не требуют отдельного согласования.

Фактические версии, доступы и параметры конкретных конфигураций помечены «Требуется от стенда». Их нельзя заменять догадками или выдавать симуляцию за реальную проверку. Неизвестность стенда блокирует соответствующую интеграцию и её приёмку, но не всю разработку.

## 1. Первый принимаемый результат

Первый результат — небольшой технический spike и воспроизводимый отчёт: реальные версии, команды без секретов, права, восстановление .dt/.bak в новые базы, подготовка, verify и удаление созданных ресурсов. Проверять прежде всего путь архива, а не EDT. Допускается сдавать spike частями по форматам, явно отмечая непроверенный формат.

Следующий результат — сквозной сценарий через минимальный UI/API и настоящий Windows-агент: выбор архива → заказ → новая база → подготовка → проверка → подключение. Один каркас приложения не считается этим результатом. Без стенда можно принять каркас и контрактные тесты отдельно, но нельзя закрыть spike или MVP.

## 2. Порядок roadmap

Да, порядок меняется: сначала вертикальный сценарий заказа из архива. API, минимальный UI, SQL-метаданные, очередь, агент и необходимая часть engine развиваются вместе. Git/EDT/сборка CF и обновление существующих баз идут после рабочего заказа архивов и не являются его зависимостью. Обновлённый порядок — в [roadmap.md](roadmap.md).

## 3. Последовательная приёмка сценариев

Разрешена. Базовый порядок: .dt с локального диска агента; .bak с проверкой доступа службы SQL, включая UNC/раздельные хосты; пустая база как отдельный пользовательский сценарий; опубликованный SQL-шаблон поверх общего механизма восстановления. Реализатор может поменять порядок .dt/.bak по доступности образцов, не исключая ни один формат.

Завершённый MVP включает оба формата, пустую базу и SQL-шаблон. Приёмка одного формата — промежуточный этап, не сокращение MVP. Git/CF-сценарии принимаются последующим этапом проекта.

## 4. Версии 1С, EDT, Vanessa Runner, SQL и Windows

**Требуется от стенда.** Точные установленные версии не предоставлены. Целевое направление: компоненты 1С x64, Windows Server 2022 для агента; SQL Server целевого тестового пула. Это ориентир, не подтверждённый паспорт среды. SQL Server 2022 можно использовать как базу нового стенда, если он согласован администратором и совместим с используемой платформой/архивами.

В spike зафиксировать полный build платформы/клиента/RAS, версии и совместимость SQL, ОС и runtime. EDT, Vanessa Runner и OneScript вне критического пути заказа архивов; не выбирать их вслепую и не блокировать ими первый сценарий. Число «3.x» в старой спецификации — направление проверки Vanessa Runner, не подтверждённая установленная версия. Паспорт заполняется по [stand-readiness.md](stand-readiness.md).

## 5. .NET, Node.js и frontend

Корпоративные ограничения неизвестны. Базовое решение нового проекта: .NET 10 LTS / ASP.NET Core / EF Core согласованной основной версии, Node.js 24 LTS, npm, React + TypeScript. Node нужен для сборки frontend, не для его исполнения на сервере. Точные совместимые версии SDK, пакетов и инструментов фиксирует реализатор в global.json, lock-файлах и инструкции сборки; не использовать плавающие latest.

Выбор веток LTS проверен по [политике .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) и [списку Node.js](https://nodejs.org/en/about/previous-releases) на дату документа. Это не означает, что эти версии уже установлены в компании. При обнаружении корпоративного запрета предложить ADR с поддерживаемой альтернативой.

## 6. Кто предоставляет стенд и когда

Стенд, лицензии, архивы и доступы предоставляет владелец проекта совместно с его администраторами. Срок и готовность **не подтверждены**. Реализатор предоставляет точный перечень доступов, инструкции установки, диагностический скрипт без вывода секретов и требования к тестовым данным. Базу/сервер в рабочей инфраструктуре не считать разрешённым стендом только потому, что он доступен по сети.

Для первого этапа нужен хотя бы небольшой разрешённый .dt или .bak и необходимые компоненты восстановления. Тестовый EDT-проект потребуется позже. Пока стенда нет, реализовать домен, API, контракты, симуляцию для разработки и тесты; явно отделять их результаты от интеграционной приёмки.

## 7. Разрешённые создание и удаление

Только новые ресурсы выделенного тестового пула с reservation и журналом владения. Базовые префиксы: bs_test_ для личных ИБ/SQL БД, bs_ci_ для одноразовых CI-ресурсов; добавлять уникальный идентификатор, а отображаемое название хранить отдельно. Префиксы настраиваются и подтверждаются при настройке пула.

Имя не доказывает владение. Перед удалением нужны совпадение идентификаторов ресурса и записи reservation, подтверждённая история создания и отсутствие конфликтующей операции. Существующие базы не усыновляются автоматически. Пул выключен до явной настройки разрешённых серверов и областей размещения администратором.

## 8. Размещение API, UI и метаданных

Базовая схема MVP: API как Windows-служба ASP.NET Core, React как статические файлы того же приложения, один HTTPS origin. Reverse proxy/IIS можно использовать, если это стандарт инфраструктуры, но это не обязательная зависимость разработки. Контейнеры и Linux-развёртывание не требуются для первой приёмки.

API и агент могут находиться на одной Windows ВМ, но работают отдельными процессами и учётными записями. SQL-метаданные — отдельная БД BuildSystem на разрешённом SQL Server. Тестовые ИБ/SQL обычно размещаются на существующем тестовом пуле, отдельно от сборочной ВМ. Это предполагаемая схема, а не уже выданные хосты.

## 9. Один хост или несколько

**Требуется от стенда:** реальная топология неизвестна. Поддержать настройкой оба варианта; не зашивать localhost, общую букву диска или общую учётную запись. Первый локальный spike допустим на одном изолированном хосте. До итоговой приёмки проверить .bak с SQL на другом хосте и доступом службы SQL к staging.

Администратор заполняет матрицу: пользователь → HTTPS API; агент → HTTPS API; агент → SQL/RAS/сервер 1С; агент → archive root; SQL service → backup staging. Порты и направления определяются фактической настройкой. Git нужен только этапу сборки.

## 10. Аутентификация к SQL, RAS и Git

Предпочтение для SQL/UNC — отдельные Windows service accounts и integrated authentication. gMSA допустима при поддержке домена. SQL authentication разрешается как явная настройка стенда с секретом в локальном хранилище агента. Не требовать sysadmin у повседневного агента по умолчанию: реализатор составляет перечень операций и предлагает минимальный профиль/контролируемый механизм создания БД.

Аутентификацию администрирования кластера/RAS проверить на выбранной платформе; CredentialRef относится к нужному уровню доступа, а не заменяет права ОС. Учётные записи создаёт администратор, права проверяет spike. Git позже: отдельный deploy key или токен репозитория, без личного пароля пользователя. Конкретный разрешённый механизм **требуется от стенда**.

## 11. Хранилище CredentialRef

Базовое решение Windows MVP: локальное хранилище секретов на исполняющем агенте, DPAPI в контексте сервисной учётной записи и ACL каталога. Администратор заполняет его отдельной локальной CLI-командой с интерактивным вводом/защищённым stdin, не аргументом командной строки. CredentialRef — непрозрачный ключ, не сам секрет.

API хранит ссылки и разрешённую связь project/pool/agent/credential; общий endpoint чтения секретов отсутствует. План подписывается/выдаётся только доверенному агенту и проверяет разрешённые ссылки; пользователь не подставляет произвольный CredentialRef. Пароли не проходят через YAML, outputs и логи. Секреты API/его SQL и ключи веб-приложения защищаются отдельно на API-хосте. Миграция в корпоративный vault возможна через интерфейс провайдера, но не обязательна для MVP.

## 12. Регистрация и доверие агенту

Базовое решение: администратор создаёт одноразовый enrollment token со сроком 15 минут, ограниченный ожидаемым агентом/пулом. Агент обращается по проверенному HTTPS; до административного подтверждения зарегистрированный агент находится в Pending и задания не получает. Повторное использование/истечение token отклоняется.

После подтверждения выдаётся отдельный криптографически случайный agent token, ограниченный его идентификатором и полномочиями. На сервере хранится проверочное хеш-значение, у агента секрет защищён DPAPI. Нужны отзыв, ротация и аудит; самозаявленные capabilities не дают права на чужие пулы/секреты. Enrollment выполняется администратором в доверенной сети. При корпоративном требовании mTLS допускается заменить механизм через ADR, не отключая проверку HTTPS.

## 13. Вход пользователей

Корпоративный OIDC/AD-провайдер **не предоставлен**. Чтобы не блокировать изолированный MVP, базовый вход — локальные учётные записи ASP.NET Core Identity, cookie-сессии, CSRF-защита, блокировка перебора и HTTPS. Пользователей создаёт администратор; публичной регистрации нет. Первый администратор создаётся bootstrap-командой без пароля в репозитории или логах. Recovery key/ключи защиты cookie сохраняются защищённо и не теряются при рестарте.

OIDC — отдельный расширяемый провайдер, не самостоятельная реализация LDAP-протокола. Если компания запрещает локальные учётные записи, до подключения реальных пользователей нужен согласованный IdP и адаптация; разработка остальных компонентов продолжается.

## 14. Роли и проекты

Для MVP достаточно Developer и Administrator. Членство хранится в ProjectMemberships(UserId, ProjectId, Role/Permissions) и задаётся администратором; без членства разработчик не видит источники/заказы проекта. Администратор может настраивать систему и управлять окружениями с аудитом. Наличие роли Developer само по себе не даёт доступа ко всем проектам.

## 15. Совместный доступ

В первом MVP достаточно владельца и администратора. Общий ACL/приглашения другим разработчикам отложены; существующее упоминание ACL означает возможность расширения, не обязательный экран MVP. Административный доступ в веб-систему не означает автоматическое получение прикладных прав внутри 1С.

## 16. Пользователь внутри ИБ

Базовый вариант без обязательного домена: отдельный пользователь 1С для владельца, назначаемый профилем конкретной конфигурации с нужными тестовыми ролями. При наличии домена предпочтителен маппинг на Windows-учётную запись владельца; способ задаётся политикой проекта, а не определяется автоматически по совпадению имени.

Если нужны логин/пароль 1С, пароль генерируется отдельно на каждое окружение и выдаётся только владельцу в аутентифицированном интерфейсе однократного получения по HTTPS, без пароля в .v8i, URL, почте и логах. Временная выдача имеет TTL, защищённое хранение и аудит без значения секрета; при потере используется сброс/повторная генерация, а не повторное раскрытие старого значения. Реальная процедура создания пользователя, bootstrap-доступ и допустимые роли **требуются от профиля проекта**; без них база не Ready.

## 17. Первые каталоги и ACL

**Требуется от стенда:** реальные local/UNC-пути и исполнители неизвестны. Нельзя считать примеры путей действующими. Администратор регистрирует ArchiveRoot, привязывает агент/группу и разрешённые проекты. Реализатор делает конфигурацию и диагностику доступа именно из сервисного контекста. Для первого spike достаточно одного явно разрешённого каталога; для MVP проверить и локальный источник, и UNC.

## 18. Завершённость файла

Базовый протокол: поставщик записывает файл под временным именем и после закрытия атомарно переименовывает в окончательное в том же каталоге/томе. Опубликованный файл больше не изменяется; новое содержимое получает новое имя. Для источника без такой гарантии — completion marker после закрытия, содержащий размер и SHA-256. Проверка только неизменного размера несколько секунд недостаточна.

Протокол выбирается настройкой root и подтверждается владельцем источника. При stage заново сверяются зафиксированный fingerprint и итоговые байты; при подмене — ArchiveChanged. Реализатор может предложить иной доказуемый протокол, не подменяя его эвристикой ожидания.

## 19. Staging и доставка .bak

Staging — управляемая системой область с отдельным бюджетом места, защищённая от пользовательской модификации. .dt исполняется из локальной staging-копии агента. Для .bak базовый вариант — выделенная UNC staging-папка, куда агент может писать, а служба целевого SQL Server — читать. При размещении на SQL-хосте локальный каталог также допустим через явное сопоставление, не через совпадение букв дисков.

Файл публикуется в staging атомарно после проверки checksum; агент/сервер удерживают ссылку, пока SQL использует backup. Если подходящего UNC нет, реализатор предлагает контролируемую доставку на SQL-хост отдельным ADR. Фактические пути, ACL и место **требуются от стенда**.

## 20. Размеры и параллелизм

**Требуется от стенда:** реальные/максимальные размеры .dt/.bak и итоговых файлов БД неизвестны. Не принимать размер архива за размер БД и не объявлять неограниченные лимиты. До измерения стартовый безопасный параллелизм — одно stage и одно восстановление на пул; максимум одно создание на пользователя. Это конфигурация, не ограничение архитектуры.

MaxArchiveBytes, MaxStagingBytes, MaxEnvironmentBytes и CapacityBytes обязательны при активации пула/root и задаются по реальному свободному месту с резервом. Пул без заполненного бюджета не принимает новые заказы. Реализатор показывает прогноз/фактический расход и обоснование изменения лимитов по результатам spike.

## 21. Ограничение места при .dt

До допуска .dt проект должен иметь измеренную консервативную оценку по разрешённым образцам и реальное ограничение ресурсов. Предпочтительный стенд: выделенный SQL instance/том для одноразовых тестов с бюджетом и свободным резервом; отдельный staging-бюджет. Одной формулы «размер .dt × коэффициент» недостаточно.

Реализатор в spike доказывает на целевой платформе, что ограничение growth/MAXSIZE или иной инфраструктурный предел действительно сохраняется после загрузки .dt и не обходится пересозданием/добавлением файлов. Если доказать per-base предел нельзя, требуется изолированный ресурс с ограниченной ёмкостью без риска для чужих БД либо .dt остаётся заблокированным в этом пуле. Watchdog свободного места — дополнительная защита, не единственная гарантия. Неподтверждённый механизм не считать реализованным.

## 22. Хранение и очистка

Базовые настраиваемые сроки: CF — 30 дней; копии staging — 24 часа после терминального задания, когда нет активного использования/неопределённого процесса; сырые логи — 30 дней; метаданные заданий — 90 дней; аудит — 180 дней. Метаданные окружений/владения сохраняются, пока нужны для действующих ресурсов и расследования.

Опубликованные шаблоны и артефакты с активными ссылками не очищаются по одному возрасту. Исходные архивы в ArchiveRoot система вообще не удаляет. SQL-backup перед обновлением существующей базы удерживается до закрытия deploy/recovery и далее по отдельной политике администратора; без неё соответствующий deploy не включается. Пути и квоты хранилищ **требуются от стенда**. Чистильщик не удаляет backup, который ещё читает SQL, даже если Job уже помечен Failed.

## 23. Профиль подготовки

Точный профиль предоставляет/подтверждает владелец конфигурации совместно с администраторами. Реализатор предоставляет интерфейс, шаблон описания и исполнение, но не угадывает, какие регистры/задания/настройки безопасно менять. Владелец проекта организует получение этого перечня; конкретные ответственные пока не назначены.

Для каждого проекта нужны: обмены и расписания, почта/SMS/ЭДО, HTTP/Web endpoints, фоновые задания, файловые каталоги, внешние БД, пользователи, обезличивание и разрешённые тестовые адреса. Для разработки допустим синтетический профиль маленькой искусственной конфигурации. No-op профиль для копии реальной базы не подтверждает подготовку и не позволяет Ready.

## 24. Сетевая изоляция

Базовое требование — отдельный тестовый сегмент/хосты с outbound allowlist: только согласованные API, SQL, RAS, архивное хранилище и тестовые сервисы. Рабочие SMTP, интеграции и файловые ресурсы недоступны до и во время первого запуска прикладного кода. Фактические firewall-правила предоставляет администратор, реализатор включает их проверку в паспорт/приёмку.

Нельзя обещать изоляцию отдельной ИБ обычным host firewall, если она находится в одном процессе/хосте с рабочими базами и имеет те же сетевые доступы. При такой топологии нужен отдельный тестовый кластер/host/process boundary с доказуемой изоляцией. Отсутствие нужной границы — блокер выдачи реальной копии, не повод выключить проверку.

## 25. Регламентные задания при восстановлении

Цель фиксирована: задания запрещены до восстановления/регистрации, во время загрузки и до окончания подготовки. Точные средства и устойчивость запрета при .dt проверяет spike на полном build платформы. Для .bak регистрация выполняется сразу с запретом заданий; для .dt запрет устанавливается до загрузки и проверяется после неё, но одна последующая проверка не доказывает отсутствие окна запуска во время загрузки.

Если платформа не гарантирует запрет на всём интервале, использовать отдельный тестовый кластер с предварительно отключённым механизмом запуска заданий/иным проверенным ограничением. Сетевая изоляция обязательна дополнительно. Конкретные CLI-ключи здесь намеренно не выдуманы; без реальной проверки механизм не принят.

## 26. Перенесённые пользователи и секреты

Решение задаётся профилем: запретить доступ перенесённых пользователей/Windows mappings, заменить рабочие сервисные учётные данные, создать/назначить владельца и ограниченный технический bootstrap-доступ. Удалять всех пользователей без учёта ссылок/конфигурации нельзя; допустима блокировка или замена по проверенной процедуре.

В профиль входит перечень embedded-секретов/ключей интеграций и правила обезличивания. Учётная запись, нужная для начальной подготовки, берётся из защищённого CredentialRef и не выдаётся владельцу базы. Неизвестные пользователи/доступы и отсутствие bootstrap-доступа — причина остановки подготовки, а не публикации с исходными паролями.

## 27. Код подготовки

Единый контракт TestIsolationProvider и версионированный артефакт профиля. Для первого проекта реализатор может предложить проверенную внешнюю обработку, расширение или штатный API конфигурации; конкретный механизм зависит от конфигурации и доступа. Не вводить обязательный универсальный способ до spike.

Код профиля хранится в Git, проходит ревью, публикуется с версией/checksum и выбирается администратором. Исполнитель не принимает произвольный код/путь от разработчика и не скачивает изменяемый latest. Изменения прикладных настроек подтверждает владелец конфигурации; инженерную реализацию можно поручить реализатору после получения перечня.

## 28. Что доказывает verify

Обязательные результаты: фактическая SQL БД и регистрация ИБ соответствуют reservation; нет незавершённого восстановления/конфликтующей операции; тестовое подключение успешно; ожидаемые источник/checksum и версия конфигурации зафиксированы; профиль подготовки нужной версии прошёл и его постусловия проверены; права владельца работают, перенесённые доступы не действуют; изоляция подтверждена.

Для пустой базы — административное подключение и отсутствие обещания прикладного интерфейса. Для .dt/.bak/шаблона — чтение ожидаемых прикладных контрольных данных и тестовый запуск разрешённого сценария без рабочих побочных действий. Для CF — дополнительно ожидаемая версия конфигурации и завершённое обновление БД. Конкретные контрольные запросы предоставляет профиль проекта.

«Exit code = 0», «ошибок в логах нет» и один boolean агента недостаточны. Нужны структурированные результаты проверок с JobId/attempt, идентификаторами ресурсов, версией профиля и временем. Отсутствие рабочих интеграций подтверждают одновременно инфраструктурная allowlist и проверка настроек; не пробовать посылать реальную почту/платёж как тест.

## 29. Кто меняет YAML

В MVP определения хранятся в Git и изменяются через PR; администратор импортирует/активирует конкретную проверенную версию. Разработчик выбирает готовый сценарий и вводит разрешённые параметры. Онлайн-редактор YAML не обязателен. Сохранённые snapshots/plan hashes неизменяемы; обновление определения не меняет активные задания. Реализовать валидатор и понятные сообщения, а не произвольный shell.

## 30. Поддержка синтаксиса

Для первого вертикального среза обязательны параметры, типизированные expressions, последовательные steps, registry, timeout и retry с maxAttempts=1 для изменяющего восстановления. Неподдерживаемые поля отклоняются компилятором, не игнорируются.

finally и when: safe-to-unlock допускается реализовать перед включением сценария обновления существующей ИБ; до этого пример deploy-existing явно помечается как последующий этап, а не обещание работающего MVP. safe-to-unlock — встроенная именованная политика из закрытого реестра, не пользовательское выражение. Она проверяет подтверждённую готовность ИБ, текущую блокировку/владение и отсутствие неопределённой операции; при сомнении false. Cleanup не гарантируется при падении агента и не заменяет reconciler.

## 31. Журнал операций

Авторитетный журнал намерений/ресурсов — в SQL-метаданных API: reservation, operation id, attempt, fencing token, intent до внешнего действия, результат и внешние идентификаторы. Нужен durable локальный журнал агента для процессов и неподтверждённых событий; базовый вариант SQLite с ACL без секретов. Это не вторая авторитетная база состояния.

Перед действием должны быть серверное разрешение/intent и локальная запись; новый destructive intent при недоступном API не начинается. Сохраняются PID + время старта/идентификатор экземпляра, SQL session/request id, признак отправки команды и обнаруженный исход. После рестарта проверяются реальные процессы, результаты передаются идемпотентно и сверяются сервером. Один PID не считается доказательством владения процессом.

## 32. Потеря lease и внешний процесс

При кратком обрыве связи агент может продолжать уже разрешённую операцию только пока достоверно не истёк текущий lease; до запуска любого следующего изменяющего шага lease подтверждается сервером. При истечении/отзыве lease новые изменяющие действия прекращаются, попытка не получает нового владельца с правом повторного восстановления до reconciliation. Резервирование ресурсов/блокировка ИБ не освобождаются автоматически по истечению lease.

Для локальных безопасно повторяемых checkout/compile — best effort завершить принадлежащее дерево процессов. Для .dt и LoadCfg/UpdateDBCfg — инициировать предусмотренную провайдером остановку принадлежащего локального процесса; сама остановка не означает откат/готовность. Неизвестный результат → NeedsAttention, никаких unlock, retry или DROP до сверки.

SQL RESTORE выполняется на сервере и может продолжаться после завершения клиента. Одно закрытие SqlConnection не доказывает отмену. Зафиксировать идентификатор операции, прекратить дальнейшие действия и наблюдать доступными read-only средствами. Принудительный KILL/разрушающее исправление при неизвестном исходе в MVP — операторское решение по подтверждённой операции. Различать явную отмену пользователя и потерю связи; в обоих случаях проверять действительный исход.

## 33. Автоматический и ручной reconciliation

Автоматически: прочитать состояние процессов/SQL/регистрации, повторить доставку событий, восстановить наблюдение, сопоставить ресурсы, завершить известный безопасный переход; создать cleanup-job для Failed/Cancelled, только когда исход установлен, владение подтверждено и активных операций нет. Резервирование/квота сохраняются до проверенного результата.

Оператор: неопределённое владение/исход, конфликт с чужим ресурсом, принудительное прекращение SQL, восстановление поверх существующей БД, решение о возобновлении после неоднозначной ошибки. Минимальный UI администратора обязателен: список NeedsAttention, хронология и ресурсы, обновление диагностики, разрешённые typed-действия с подтверждением и аудитом. Свободного поля SQL/shell нет; кнопка «считать готовым» не обходит verify.

## 34. Квоты и сроки

Как базовые конфигурируемые значения принять: две базы на пользователя, одно создание одновременно, TTL семь дней, одно продление до 30 дней от момента продления. Можно повторять продление при соблюдении политики; предел абсолютного возраста не задан и должен быть отдельной настройкой, если потребуется. Эти значения не были измерены на реальном пуле и могут быть изменены администратором.

Предложение для общей ёмкости и объёма на пользователя — заполнить после паспорта/замеров, не выдумывать гигабайты. В коде запрещён unbounded fallback: пулы без численных бюджетов выключены. Failed/NeedsAttention/Expired учитываются до подтверждённого удаления. Глобальные лимиты пула из вопроса 20 применяются независимо от пользовательских.

## 35. Автоматическое удаление и Expired

Да, автоматическое удаление по умолчанию выключено. Если администратор включает его для новых заказов, базовый grace period — три дня; политика и DeleteAfter сохраняются в заказе и показываются до создания базы. Изменение defaults не переносит незаметно дедлайн уже созданных окружений.

По истечении TTL окружение становится Expired: новые deploy запрещены, данные сохраняются и квота занята. По умолчанию действующие пользовательские сеансы не завершаются и вход в 1С не блокируется; это явно показывается в UI. Карточка/история подключения владельцу остаются доступны; endpoint выдачи нового connection artifact по исходной спецификации — только Ready. Для блокировки входа нужна отдельная согласованная политика пула. Перед удалением применяются правила вопроса 36 и блокировка окружения.

## 36. Активные сеансы

Для deploy базовое поведение: запрет новых сеансов, ожидание завершения текущих до настраиваемого таймаута (стартовое значение пять минут), затем отказ/NeedsAttention по действительному состоянию; без молчаливого принудительного завершения. Снятие временного запрета возможно только при доказанном безопасном состоянии и владении блокировкой.

Для удаления владелец подтверждает удаление данных. При активных сеансах также ждать до таймаута и завершить операцию ошибкой с возможностью повтора. Force-disconnect — отдельное явное действие администратора либо заранее разрешённая политика одноразового CI-пула; не право обычного владельца по умолчанию. Сеансы чужих баз не затрагиваются.

## 37. Git и ревью

Реализация — feature-ветки и PR в main небольшими принимаемыми этапами. Прямые изменения кода в main не являются рабочим процессом. В PR: задача, получившееся поведение, проверка/доказательства, ограничения стенда и миграции. Коммиты с понятными смысловыми сообщениями; строгий формат можно выбрать реализатору, обязательного шаблона нет.

Контроллер проекта (ChatGPT) выполняет архитектурное ревью и проверку соответствия документации по поручению пользователя. Окончательная продуктовая приёмка остаётся у Ивана; доступы/инфраструктурные политики подтверждают его администраторы. Автоматическое слияние реализатором не предполагается. Фактические branch protection/права не объявляются настроенными без отдельной проверки/настройки владельцем.

## 38. CI и интеграции

Базово GitHub Actions: сборка .NET/frontend, unit/contract tests, линтер/проверки на PR без доступа к внутренним ресурсам. Отдельный Windows self-hosted runner потребуется для реальной 1С/SQL; его наличие и сроки **не подтверждены**. До выдачи runner реальные интеграционные тесты можно запускать вручную тем же скриптом на разрешённом стенде с сохранением отчёта.

Интеграционный runner находится в тестовом сегменте, использует только bs_ci_ reservation и ограниченные секреты. Не запускать на нём код непроверенных fork PR и не выдавать ему рабочие credentials. Workflow с доступом к стенду — ручной/для проверенного кода. Пропущенные integration tests явно видны; зелёный unit CI не означает пройденную реальную приёмку.

## 39. Доказательства и приёмка

Spike: воспроизводимый протокол реальных версий/команд, хеши образцов, права и топология, успешные restore/prepare/verify/delete, проверки запрета заданий/изоляции, описание неудачных/непроверенных случаев. Секреты и содержимое реальных данных в отчёт не входят. Проверка одноразовой искусственной базы не доказывает совместимость всех конфигураций.

MVP: демонстрация пользователем через UI на согласованном стенде плюс автоматические тесты домена/API и интеграционные отчёты по обоим форматам, пустой базе, шаблону и существенным сбоям. Проверить idempotency, квоты, чужой доступ, смену файла, потерю агента, отмену и очистку. Критерии из disk-archives.md и test-environments.md обязательны. Нет стенда/профиля — статус «не проверено», а не «принято».

Реализатор готовит доказательства; контроллер проекта проводит ревью; Иван принимает продуктовый результат. Согласованный администратор подтверждает инфраструктурную изоляцию и допустимость работы с выбранными данными. Конкретный человек/окно демонстрации ещё не назначены.
