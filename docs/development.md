# Разработка: первый инженерный срез

## Границы поставки

Этот срез реализует чистые доменные правила и unit-тесты. Это не работающий заказ базы, не технический spike и не завершённый MVP. API, UI, EF Core/миграции, Windows-служба агента и реальные CLI-провайдеры будут добавляться отдельными изменениями. Не создаём пустые проекты для ещё не реализованных компонентов: целевая структура остаётся в architecture.md.

Реальные 1С/SQL/UNC и изоляция не проверялись; паспорт стенда — stand-readiness.md. Тесты используют искусственные идентификаторы и свидетельства и не доказывают фактическую подготовку базы.

## Требования и сборка

Установить .NET SDK **10.0.402**, зафиксированный в global.json. Если SDK установлен локально, добавить его каталог в PATH. Roll-forward отключён: обновление SDK — явное изменение через PR. Для этого среза Node.js не требуется. Frontend появится отдельно с Node.js 24 LTS и npm lock-файлом.

Из корня репозитория (одинаковые команды в Windows PowerShell и Linux):

```text
dotnet --version
dotnet restore BuildSystem.slnx --locked-mode
dotnet build BuildSystem.slnx --configuration Release --no-restore
dotnet test BuildSystem.slnx --configuration Release --no-build --no-restore --logger trx --results-directory TestResults
```

Источник пакетов явно задан в NuGet.Config (nuget.org, без наследования пользовательских feeds). NuGet-зависимости зафиксированы прямыми версиями и packages.lock.json. При намеренном обновлении пакетов выполнить `dotnet restore BuildSystem.slnx --force-evaluate`, проверить diff lock-файлов, затем повторить сборку и тесты в locked mode. Nullable и предупреждения как ошибки включены для всех проектов.

## Архитектурные ограничения

- Домен не выполняет SQL, CLI, сеть или чтение секретов.
- Снимок квот должен отражать не только статус окружения, но и незавершённые операции по серверному журналу. NeedsAttention/Failed не доказывают прекращение RESTORE; слот параллельного создания удерживается до reconciliation.
- Проверка квоты по снимку — только правило принятия решения. В будущем API обязан читать снимок, проверять лимиты, создавать reservation/заявку и записывать задание в одной защищённой от write skew транзакции. In-memory unit-тест не доказывает конкурентную безопасность SQL.
- Локальная проверка версии объекта не заменяет атомарный rowversion/ETag check при записи в БД. Устаревшая версия отклоняется и при повторном удалении; при актуальной версии повтор в Deleting/Deleted возвращает уже назначенное задание. Обработку HTTP-повторов и Idempotency-Key реализует будущий application/API слой.
- Структурированные свидетельства проверки должны поступать из доверенного серверного журнала текущей попытки с проверкой lease, отмены и результатов обязательных шагов. Конструктор доменного объекта сам по себе не доказывает истинность этих свидетельств.
- ResourceIdentity обозначает заранее зарезервированный слот, а не уже известный UUID регистрации или incarnation SQL БД. Реальные идентификаторы и история создания привязываются к слоту в будущем durable resource journal; совпадение имени не подтверждает владение.
- Удаление допускается только после установления исхода внешних операций и подтверждения владения. Отсутствие регистрации ИБ и SQL БД подтверждается отдельно; истечение lease не означает отсутствие ресурсов.

## CI и работа с Git

Работа ведётся в feature-ветке через PR в main. GitHub Actions выполняет locked restore, Release build и доменные тесты на Linux и Windows. В этом workflow нет внутренних секретов, сетевого доступа к стенду или self-hosted runner. Реальные integration tests должны запускаться отдельно на разрешённом стенде для проверенного кода. Локальное прохождение тестов не означает, что удалённый workflow уже выполнен.

Для PR указать задачу, реализованное поведение, команды и результаты проверок, ограничения и миграции. Данный срез миграций не содержит. Автоматическое слияние не предусмотрено.
