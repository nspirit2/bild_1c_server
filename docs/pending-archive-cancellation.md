# Отмена заказа архива до первой аренды

Отдельный серверный переход для обычного `ProvisionArchive` с текущим форматом снимка заказа. Сервис по умолчанию выключен и пока не подключён к HTTP/API или UI. Новая миграция добавляет журнал подтверждений без переклассификации существующих заказов. Не распространяется на `ObserveArchiveStage`, получившие аренду задания, готовые окружения, очистку staging или удаление SQL/1С. Свидетельства регистрации и их подтверждения остаются только диагностическими и не участвуют в решении.

- Авторизация: текущий владелец с членством в проекте либо действующий администратор. Сначала проверка полномочий, затем раскрытие состояния; при повторном запросе проверка выполняется снова. Веб-команда — явный POST с существующей защитой CSRF, без автоматического запуска или повторов в UI.
- Транзакция Serializable с блокировками `agent-control → owner → root → pool`. Ключи блокировок относятся к самому заказу, а не к администратору. Предварительно прочитанные ключи — только подсказка; ссылки на владельца, источник, пул и резерв перепроверяются под блокировками. Не использовать транзакцию общих операций агента, которая может заодно обновить просроченные аренды других заказов.
- Допустим только согласованный снимок `Pending / Pending / Requested / Held` с исходным неразрешённым состоянием provisioning и без какой-либо исторической аренды, артефакта или учётной записи о ранее выданном полномочии. Недостаточно увидеть отсутствие активной аренды. При повреждении связей или неполных данных операция отклоняется, резерв сохраняется.
- В одной транзакции фиксируются терминальное состояние `Cancelled`, устойчивое подтверждение перехода, событие аудита, сброс признака незавершённой операции и освобождение резерва. Идентификаторы, исходные суммы и запись заказа сохраняются. Это не `Deleted`; запись не свидетельствует о проверке либо удалении SQL/1С. Для отмены не создаётся запись об освобождении staging после физической очистки.
- Квота исключает отменённый заказ только при согласованном освобождённом резерве и подтверждённом переходе. Повторный запрос возвращает сохранённый результат, не изменяет квоту и не дублирует аудит. Повтор исходного заказа с тем же ключом не восстанавливает отменённое задание.

## Отображение истории

Статус stage может подтвердить `CancelledBeforeFirstLease` только по неизменяемой записи с точными идентификаторами и согласованным терминальным состоянием. Сырые значения `Cancelled` или `Released` сами по себе не доказывают снятие удержания. При противоречии статус недоступен, а не заменяется на «ожидает аренды». Исторические объёмы отображаются как исторические. Для подтверждённой отмены cleanup неприменим: не выдавать запись `StagingReleased`, не утверждать, что агент что-либо удалил, и не показывать освобождение по ledger очистки.

Ключевые проверки: если отмена побеждает выдачу первой аренды, агент больше не может получить это задание; если побеждает выдача аренды, отмена ничего не освобождает. Проверить также историческую аренду, повреждённые ссылки, отказ до commit, повтор после потери ответа, повторное использование квоты и отсутствие изменений в других заказах. Проверки на одноразовой SQL-базе не заменяют приёмку на стенде. До проверки транзакции маршрут и пользовательское действие не добавляются.
