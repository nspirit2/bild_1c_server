# Отмена заказа архива до первой аренды

Отдельный серверный переход для обычного `ProvisionArchive` с текущим форматом снимка заказа. Сервис и HTTP-команда выключены по умолчанию. В интерфейсе оператора команды отмены нет. Новая миграция добавляет журнал подтверждений без переклассификации существующих заказов. Не распространяется на `ObserveArchiveStage`, получившие аренду задания, готовые окружения, очистку staging или удаление SQL/1С. Свидетельства регистрации и их подтверждения остаются только диагностическими и не участвуют в решении.

- Авторизация: текущий владелец с членством в проекте либо действующий администратор. Сначала проверка полномочий, затем раскрытие состояния; при повторном запросе проверка выполняется снова. Веб-команда — явный POST с существующей защитой CSRF, без автоматического запуска или повторов в UI.
- Транзакция Serializable с блокировками `agent-control → owner → root → pool`. Ключи блокировок относятся к самому заказу, а не к администратору. Предварительно прочитанные ключи — только подсказка; ссылки на владельца, источник, пул и резерв перепроверяются под блокировками. Не использовать транзакцию общих операций агента, которая может заодно обновить просроченные аренды других заказов.
- Допустим только согласованный снимок `Pending / Pending / Requested / Held` с исходным неразрешённым состоянием provisioning и без какой-либо исторической аренды, артефакта или учётной записи о ранее выданном полномочии. Недостаточно увидеть отсутствие активной аренды. При повреждении связей или неполных данных операция отклоняется, резерв сохраняется.
- В одной транзакции фиксируются терминальное состояние `Cancelled`, устойчивое подтверждение перехода, событие аудита, сброс признака незавершённой операции и освобождение резерва. Идентификаторы, исходные суммы и запись заказа сохраняются. Это не `Deleted`; запись не свидетельствует о проверке либо удалении SQL/1С. Для отмены не создаётся запись об освобождении staging после физической очистки.
- Квота исключает отменённый заказ только при согласованном освобождённом резерве и подтверждённом переходе. Повторный запрос возвращает сохранённый результат, не изменяет квоту и не дублирует аудит. Повтор исходного заказа с тем же ключом не восстанавливает отменённое задание.

## Отображение истории

Статус stage может подтвердить `CancelledBeforeFirstLease` только по неизменяемой записи с точными идентификаторами и согласованным терминальным состоянием. Сырые значения `Cancelled` или `Released` сами по себе не доказывают снятие удержания. При противоречии статус недоступен, а не заменяется на «ожидает аренды». Исторические объёмы отображаются как исторические. Для подтверждённой отмены cleanup неприменим: не выдавать запись `StagingReleased`, не утверждать, что агент что-либо удалил, и не показывать освобождение по ledger очистки.

Список операций поддерживает `state=Cancelled`. Сервер проверяет подтверждение до формирования страницы, исключая противоречивые записи. Только подтверждённая строка содержит `cancellationCode: CancelledBeforeFirstLease`; её staging-объём — исторический резерв, а не доступное место на диске. Список остаётся доступным при отключённой команде отмены. Проверка снимка использует `OPENJSON`: для базы метаданных требуется уровень совместимости SQL Server не ниже 130. Это требование не относится к базам 1С в целевом пуле.

## Контракт HTTP

Предусмотрен отдельный `POST /api/test-environments/{id}/pending-archive-cancellations` с флагом `PendingArchiveCancellation:Enabled` (по умолчанию выключен). Требуются пользовательская cookie Identity и штатный `X-CSRF-TOKEN`. Тело содержит только `expectedJobId`: это защита от отмены другого задания, а не полномочие. Успешный ответ и подтверждённый повтор содержат только `environmentId`, `jobId`, `code: CancelledBeforeFirstLease` и `cancelledAt`. Недоступный и отсутствующий заказ не различаются. Потеря ответа не означает ни успешную отмену, ни отказ; сначала следует проверить состояние, без автоматического повтора POST. Кнопка оператора не входит в этот срез.

## Проверки

Ключевые проверки: если отмена побеждает выдачу первой аренды, агент больше не может получить это задание; если побеждает выдача аренды, отмена ничего не освобождает. Проверить также историческую аренду, повреждённые ссылки, отказ до commit, повтор после потери ответа, повторное использование квоты и отсутствие изменений в других заказах. Проверки на одноразовой SQL-базе не заменяют приёмку на стенде. [SQL CI для `928b382`](https://github.com/nspirit2/bild_1c_server/actions/runs/45133870947) выполнил 355 тестов, включая все пять исходных сценариев отмены. [SQL CI для `0026452`](https://github.com/nspirit2/bild_1c_server/actions/runs/45135875865) подтвердил оба порядка отмены и выдачи первой аренды, а также откат после записи и до commit. Локальные HTTP-тесты проверяют cookie Identity, antiforgery и допустимые поля ответа; [интеграционный сценарий](../tests/BuildSystem.IntegrationTests/SqlPendingArchiveCancellationTests.cs) дополнительно проверяет реальный вход, SQL-повтор и отзыв членства. Настройка флага и добавление кнопки оператора не являются частью этой проверки.
