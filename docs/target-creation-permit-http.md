# Protected creation permit metadata HTTP

## Scope

Default-off HTTP facade over existing immutable permit ledger. No new execution authority, no worker, target mutation, lease claim or secret-bearing response. All receipts remain Executable=false and ScheduledJobsMustRemainBlocked=true. Explicit credential ID and endpoint mapping ID are pinned through IssueWithCredentialAsync only; legacy unbound issuance has no HTTP route.

## Routes

* Administrator POST `/api/admin/target-creation-permits/issue`: exactly `operationId`, `expectedOperationRevision` (lexical 1), `credentialId`, `endpointMappingId`. Permit ID and attempt ID are generated by the trusted server, not accepted from HTTP. Returns201 metadata and Location.
* Administrator GET `/api/admin/target-creation-permits/{permitId}`: historical metadata, never a grant.
* Administrator POST `/api/admin/target-creation-permits/{permitId}/revoke`: exactly `expectedPermitRevision` (lexical1 or2). Immutable pins remain retained. Revoke does not undo any external phase.
* Assigned-agent POST `/api/agents/target-creation-permit-starts`: exactly `permitId`, `expectedPermitRevision` (lexical1), `attemptId`. Current Approved token and assignment are checked by ledger; no ambient administrator authority. An exact replay yields historical NewlyRecorded=false, not new physical execution authorization. Existing service may return an already-started, subsequently Revoked receipt on exact replay; this preserves history only. A Prepared-then-revoked permit cannot record a first start. The HTTP start gate additionally requires CredentialBindingEnabled, but legacy null-pair rows remain historical metadata compatible with the underlying service, never eligible for credential delivery.

Admin routes require Administrator authorization, current DB role and CSRF on POST. Machine route uses one explicit Bearer token, no Origin, and only its exact route carries existing machine CSRF marker. Cookie alone does not authorize it. HTTPS is checked before redirect on both prefixes; forwarded headers do not establish trust. Strict4KiB UTF8 JSON rejects unknown, duplicate, missing or wrongly-cased fields, invalid GUID-D, unsafe revisions and extra permit/attempt fields on issuance. No request values in errors.

## IDs and uncertain issuance

Server-generated IDs maintain existing trusted-caller policy. Each issue POST proposes a new permit/attempt pair. Existing unique operation/attempt ledger prevents replacing/reissuing an already pinned attempt, including repeated HTTP POST. There is no automatic HTTP issuance retry, adoption or reset. If the response is lost, the issue result is unknown; do not generate fresh authority by retrying. Existing row remains durable and conflicts; known-ID GET or operator metadata reconciliation is required. A future by-operation lookup can improve discovery but cannot renew or consume a permit.

## Gates and response boundaries

`TargetCreationPermitHttp:Enabled=false` is independent from existing `TargetCreationOperation:Enabled`, `TargetCreationPermit:{Enabled,AgentStartEnabled,CredentialBindingEnabled}`. The facade cannot enable those flags implicitly. Admin issuance still requires exact canonical credential binding/nonrevoked credentials and current admission, and start repeats current authentication/admission/credential checks before replay. SQL-time first-start window stays `[IssuedAt,StartBefore)`, five minutes; a historical start replay after deadline is metadata, never freshness evidence. Credential delivery separately enforces its own current deadline.

Every prefix response including authentication/CSRF/body-limit failures gets no-store/Pragma/nosniff. Handler DI, parser and serialization failures are contained behind fixed-code error mapping; after response starts the connection aborts rather than appending errors. No raw exceptions, body, tokens, credentials, ciphertext or process diagnostics are logged. Output contains existing metadata graph only, not secrets. Diagnostics configuration remains separate and does not enable permit mutation.

## Deliberately absent

No permit UI, agent permit HTTP client/worker orchestration, physical namespace/absence checks or CREATE/restore/drop; no live/stand deployment. Even opt-in HTTP start records metadata, not a physical claim.
