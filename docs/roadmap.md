# План реализации и приёмки

Порядок изменён в пользу обязательного сценария заказа базы из архива. Подробные ответы на 39 вопросов — [implementation-decisions.md](implementation-decisions.md). Фактические данные стенда — [stand-readiness.md](stand-readiness.md); пустой паспорт не заменяется предположениями.

## Этап 0. Паспорт и технический spike архивов
Подготовить требования к стенду и проверить реальные команды создания ИБ, загрузки .dt, восстановления .bak, регистрации, запрета заданий, подготовки, verify и удаления. Первым принимаемым результатом является воспроизводимый отчёт, допускается отдельная сдача по формату. Непроверенное явно указать. EDT/Vanessa/OneScript не блокируют этот этап.

При отсутствии стенда параллельно начать каркас, домен и контрактные тесты. Такой результат принимается как отдельная инженерная часть, но не как успешный реальный spike.

## Этап 1. Первый вертикальный срез
Минимальный API/UI, SQL-метаданные, локальный вход и project membership, доверенный Windows-агент, очередь/lease, process runner, durable журнал и engine для последовательных шагов. Каталог разрешённых архивов, staging, reservation и квоты входят сразу, а не достраиваются после неконтролируемого восстановления.

Основной путь: .dt с диска → заказ через интерфейс → новая клиент-серверная ИБ → подготовка → verify → подключение владельца. По доступности стенда реализатор может начать с .bak, зафиксировав порядок в PR. Симуляция — средство разработки, не доказательство реального восстановления.

## Этап 2. Оба формата и полный заказ баз
Добавить/проверить оставшийся формат .dt/.bak, локальные и UNC-источники, доступ службы SQL к staging и раздельное размещение SQL/агента. Принять пустую базу как отдельный сценарий и опубликованный SQL-шаблон через общие провайдеры. Оба формата обязательны для завершённого MVP.

Результат: создание личных баз без Git/EDT и без ручной публикации шаблона для каждого дискового файла. Проверить source fingerprint, реальное ограничение ёмкости, права внутри ИБ и отсутствие рабочих побочных действий.

## Этап 3. Восстановление после сбоев и жизненный цикл
Идемпотентность, конкурентные квоты/блокировки, отмена, потеря связи/агента, reconciliation, cleanup с проверкой владения. UI NeedsAttention для администратора. «Мои базы», продление, удаление, expiration worker, явная политика автоудаления. Тесты отказов из disk-archives.md и test-environments.md.

Этапы 1–3 можно разрабатывать небольшими PR параллельно по компонентам, но реальная приёмка нового ресурса включает безопасность и управление его остатками. Нельзя объявлять MVP завершённым до этапа 3.

## Этап 4. Сборка CF и развёртывание
Отдельный spike EDT/Vanessa Runner/OneScript на полном наборе целевых версий. Git SHA, отдельный workspace, сборка CF и проверка артефакта. Заказ новой ИБ из готового CF/ветки использует общий engine.

До включения обновления существующей ИБ реализовать finally и встроенную политику safe-to-unlock, резервную копию и её проверку, сеансы, LoadCfg/UpdateDBCfg, verify/recovery. Автоматический RESTORE поверх существующей ИБ не входит в MVP. Этот этап не является зависимостью обязательного заказа архивов.

## CI и доказательства
На PR — воспроизводимые build/unit/contract checks. На согласованном Windows-стенде — реальные integration tests; выделенный runner ещё не предоставлен, допустим ручной запуск тем же скриптом. Отчёты фактических проверок, симуляции и пропущенных сценариев различаются явно.

Техническое ревью и проверка спецификации — контроллер проекта; окончательная продуктовая приёмка — Иван. Доступы и фактическую изоляцию подтверждают администраторы.

## Что требует сведений от владельца/администраторов
Полные версии платформы/SQL/ОС и топология; учётные записи/права; разрешённые local/UNC-каталоги и образцы; staging и бюджеты; профиль подготовки проекта с bootstrap-доступом, пользователями и проверками; гарантия сетевой изоляции и запрета заданий. Срок предоставления стенда не подтверждён. Это блокеры соответствующей реальной интеграции, а не запрет начинать независимую разработку.
