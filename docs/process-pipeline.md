# ProcessRunner и минимальный Pipeline Engine

## Границы пакета

Независимые библиотеки `BuildSystem.Agent.Tools` и `BuildSystem.Agent.Execution`. Это подготовка к archive pipeline, не включение реального восстановления. Windows Worker по-прежнему рекламирует только ControlPlaneProbe; API не выдаёт ProvisionArchive. Отсутствуют реальные обработчики 1С/SQL/Git/EDT и integration с серверным immutable plan store/resource journal.

Ветка `feat/process-pipeline-foundation` зависит от агентского пакета; подтверждение SQL-прогона сохранено отдельным коммитом `6b63e84`. Автоматического push/merge нет.

## Безопасность внешнего процесса

Запуск должен выполняться только через серверно настроенный реестр доверенных инструментов по идентификатору, с абсолютным executable, без shell. Аргументы передаются через ArgumentList, не командной строкой. Наличие allowlist не делает любой запуск безопасным: инструмент может интерпретировать собственные аргументы, загружать плагины и исполнять код. Реальные providers обязаны фиксировать разрешённую схему аргументов и workspace; YAML не передаёт произвольный toolId/argv.

ProcessRunner завершает дерево процессов при timeout/cancellation, наблюдает exit code/PID и читает stdout/stderr параллельно. Кроссплатформенный `Process.Kill(entireProcessTree: true)` не является OS containment: если родитель уже завершился, detached/reparented потомок может пережить его. Для недоверенных инструментов и гарантированного удержания потомков нужны отдельные Windows Job Objects/Linux cgroups и стендовые проверки; этот пакет их не реализует. Нельзя обещать остановку любой фоновой операции только по PID родителя.

Kill локального SQL-клиента не доказывает остановку SQL RESTORE: эта библиотека не заменяет серверный reconciliation. Проверка CF/ИБ после CLI остаётся обязанностью providers; exit code сам по себе недостаточен.

Секреты не должны попадать в результаты/аргументы логов. Маскирование известных секретов — дополнительная защита, не универсальная детекция преобразованных/закодированных секретов. Пока не проверены параметры инструментов на целевых версиях, нельзя считать redaction достаточной для безопасной публикации всех CLI-логов.

## YAML и реестр

Компилятор не исполняет YAML. Разрешены только зарегистрированные шаги name@version, типизированные параметры и ссылки на declared outputs предыдущих шагов. Прямой shell/run/script отсутствует. Неизвестные поля, дубли ключей, неподдерживаемые YAML-конструкции и ссылки в будущее отклоняются.

Матрица текущего формата:

- root: `apiVersion: buildsystem/v1`, `kind: Pipeline`, `metadata.name`, `parameters`, `steps`;
- параметр: `type`, необязательное `required: true`; все параметры обязательны (`required: false` отклоняется), нет секретных параметров/default; значения передаются compiler отдельно;
- типы: string, int (64-bit), bool, project/infobase/reservation/archiveVersion/templateVersion/artifact (разные семантические GUID-типы);
- шаг: `id`, `uses`, `with`, `timeout` (`s`/`m`/`h`, максимум 24h, default 60m), `retry.maxAttempts` (1..3);
- retry >1 только для nonmutating + явно retry-safe регистрации;
- выражения: только scalar целиком `${{ parameters.name }}` или `${{ steps.id.outputs.name }}`; output должен быть обязательным и объявленным у предыдущего шага. Строковая интерполяция отсутствует;
- известные capabilities проверяются compiler; executor проверяет pinned definition fingerprints до исполнения и перед шагом. Lease проверяется до и после handler; это не непрерывный мониторинг lease внутри операции.

Первый выпуск не реализует finally/when: они явно отклоняются. Пример deploy-existing.yaml относится к следующему этапу; его нельзя тихо выполнить без cleanup policy. Примеры archive pipeline остаются проектными: их названия шагов должны быть зарегистрированы настоящими проверенными providers перед исполнением.

Пример [control-plane-validation.yaml](../examples/control-plane-validation.yaml) — только для проверки standalone compiler при заранее заданном trusted registry `diagnostic.echo@1`; сервер его не ставит в очередь и Worker не исполняет. В production такого встроенного обработчика нет.

План должен быть неизменяемым снимком версии/схемы обработчиков и параметров, а не ссылкой на изменяемый пользовательский словарь. Реестр не содержит shell/RESTORE по умолчанию. Изменение определения обработчика после компиляции должно отклонять исполнение, а не подменять семантику плана.

## Исполнение и отмена

Шаги выполняются последовательно. Перед новой операцией и каждой попыткой проверяется lease/cancellation. Retry разрешён только зарегистрированным retry-safe шагам с ограниченным числом попыток. Неопределённый исход изменяющей операции не переводится в обычный retry.

Timeout handler — кооперативный CancellationToken, а не обещание остановить произвольный .NET-код. Неуступающий handler не должен позволять запуск следующего шага. Реальные внешние CLI обязаны использовать ProcessRunner, но серверный процесс/удалённая операция всё равно требуют отдельной сверки.

В этом пакете нет durable SQL state store/event sink для pipeline, принудительной остановки небезопасного managed-кода и сквозного publish Ready. Тестовый execution result не является серверной записью факта исполнения.

## Проверки

Process tests используют искусственный .NET console fixture: без 1С, RESTORE и реальных секретов. Проверки Linux не заменяют Windows-проверку tree kill, поведения служб и прав. Общий CI подготовлен для обеих ОС; фактический remote result фиксируется отдельно, не выводится из локальной сборки.

Pipeline tests проверяют строгую компиляцию, параметры/ссылки, registry и переходы при retry/cancellation. SQL integration suite остаётся отдельным opt-in. Поддерживаемая матрица приведена выше; фактические результаты — [отчёт ревью](process-pipeline-review.md): 124 passed, 16 SQL skipped локально, включая 22 process и 26 pipeline тестов.
