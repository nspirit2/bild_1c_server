# Развёртывание архивов с диска — обязательный MVP

## Пользовательский сценарий
«Заказать базу» → проект → «Из архива с диска» → источник/файл → название и срок → «Создать». Система сама создаёт новую тестовую базу, загружает данные, применяет тестовые настройки и возвращает подключение в «Мои базы».

Пользователю не нужно публиковать шаблон, работать с Git, запускать EDT, вручную создавать SQL БД или выполнять восстановление. Обязательный сквозной сценарий MVP — восстановить файл с диска и выдать проверенную базу.

## Форматы и расположение
| Источник | Что делает система |
|---|---|
| .dt — выгрузка информационной базы 1С | Создаёт новую клиент-серверную ИБ и загружает выгрузку средствами платформы |
| .bak — полная резервная копия одной SQL БД | Восстанавливает новую SQL БД с уникальными файлами и регистрирует ИБ в тестовом кластере |

MVP поддерживает одиночный .dt и одиночный файл полного .bak, содержащий один однозначно выбираемый backup set. Цепочки full/diff/log, striped/multifile backup и неоднозначные backup set отклоняются с понятной причиной. Расширение проверяется, но не заменяет проверку выбранным инструментом; системные БД не допускаются. CF остаётся отдельным источником конфигурации без данных.

Под «диском» понимается локальная папка хоста агента или настроенная сетевая папка UNC. Путь конфигурируется администратором один раз; выбранный файл доступен через каталог в UI. Для Windows-служб используются UNC и сервисные учётные записи; подключённый интерактивным пользователем диск не считается доступным службе.

Диск компьютера, на котором открыт браузер, не является диском сервера: загрузка файла через браузер — отдельный будущий транспорт. ZIP/7z и зашифрованные архивы не входят в эту базовую спецификацию; их поддержка потребует отдельного шага и ограничений распаковки. Базовые форматы .dt/.bak не должны зависеть от наличия архиватора.

## Каталог и доступ
Администратор задаёт ArchiveRoot: видимое имя, местоположение через серверную ссылку, разрешённые форматы, область доступа проекта, подходящих агентов и обязательный профиль подготовки. Root может быть, например, каталогом ежедневных выгрузок конкретного проекта. Разработчик видит имена файлов, относительные папки, даты, размеры и доступность; фильтрует и выбирает файл. Не видит каталоги других проектов.

Индекс обновляется фоновым заданием и вручную кнопкой «Обновить». Каталог может поддерживать подпапки и пагинацию; обход ограничен настроенным root. Недоступный агент или root не превращается в пустой успешный список. В каталог допускаются завершённые файлы: поставщик пишет под временным именем и атомарно публикует файл переименованием; для сетевого источника допускается настроенный completion marker. Система не пытается восстанавливать файл, который ещё пишется.

Версия содержит SHA-256 и размер прочитанного файла, формат и состояние. Во время индексирования проверяются завершённость и неизменность источника; недостоверный fingerprint не публикуется как Ready. Пользователь заказывает archiveVersionId, а не «последний файл по пути». Если файл заменён после выбора, старый заказ не должен молча использовать новую копию.

## Этапы задания
1. **Preflight**: ACL проекта/root, политика тестовой подготовки, доступность агента и целевого пула, резервирование ёмкости.
2. **Stage**: копирование выбранной версии в контролируемое хранилище, проверка SHA-256/размера и формата; фиксация неизменяемого ArtifactId. Исходный файл после этого не используется для восстановления.
3. **Validate**: проверка читаемости и совместимости доступными средствами целевой платформы/SQL. Для .bak — metadata/filelist и VERIFYONLY; результат не заменяет фактическое восстановление и последующий verify.
4. **Restore**: новая ИБ + загрузка .dt либо новая SQL БД + регистрация ИБ из .bak. Имена, SQL-файлы и доступы берутся из reservation, не из исходного пути или пользовательского ввода.
5. **Prepare → Verify → Publish**: общие обязательные шаги тестового окружения; только затем Ready и подключение владельцу.

Validate входит в обработчик restore-archive до изменяющих действий; stage также проверяет формат без создания ИБ. Для .dt часть ошибок совместимости выявляется только при загрузке: это явная ошибка создания, а не разрешение опубликовать непроверенную базу.

.dt должен быть доступен процессу платформы на агенте; .bak должен быть доступен службе SQL Server. При разных хостах stage обеспечивает контролируемую доставку/размещение; локальная буква диска агента не передаётся SQL Server как путь backup. До RESTORE проверяются права именно сервисной учётной записи SQL Server.

Размер архива и размер БД различаются. Для .bak оценка использует сведения о файлах, для .dt — консервативный профиль проекта и лимиты пула, уточняемые при загрузке. Без надёжного ограничения места .dt не допускается в пул. Резервируется также место staging; параллельные копирования/восстановления ограничены. Временные артефакты удаляются после освобождения всех активных ссылок и заданного retention; оригинал остаётся на диске.

## Контракты
Параметры pipeline: reservationId и archiveVersionId; пример — [provision-from-disk.yaml](../examples/provision-from-disk.yaml). В реестр типов добавляется archiveVersion. Логи содержат этап, формат, размер, checksum, длительность и понятную ошибку, но не пароли и не закрытые пути.

- archive.stage@1 принимает reservation и archiveVersion, возвращает artifactId. Повтор с тем же reservation/версией возвращает проверенный готовый артефакт либо продолжает безопасную новую временную копию; частичный файл не считается готовым.
- test.infobase.restore-archive@1 принимает reservation и artifact, возвращает infobaseId. По проверенному типу выбирает .dt или .bak. Максимум одна автоматическая попытка; после неопределённого исхода сначала reconciliation.
- preflight учитывает archiveVersion; publish требует успешные stage, restore, prepare и verify именно этой попытки и окружения.

В заявке фиксируются ArchiveVersionId, исходный checksum, итоговый ArtifactId, размещение и применённый профиль подготовки. Наличие у пользователя доступа к файлу не даёт права выбирать произвольный пул или отключать подготовку.

## Ошибки и восстановление
| Код | Поведение |
|---|---|
| ArchiveUnavailable | Источник отсутствует или недоступен; показать причину, базу не выдавать |
| ArchiveChanged | Версия не совпала при stage; предложить обновить каталог и выбрать заново |
| ArchiveInvalid | Файл повреждён, неполный или не распознаётся выбранным инструментом |
| ArchiveFormatUnsupported | Формат/тип backup вне поддерживаемого набора |
| ArchiveIncompatible | Неподходящие платформа/SQL/конфигурация; базу не выдавать |
| ArchiveQuotaExceeded | Не хватает staging/целевого места; остановить до создания ресурсов либо безопасно остановить рост |
| RestoreFailed | Известная ошибка загрузки, отслеживаемая очистка созданных ресурсов |
| RestoreOutcomeUnknown | Потерян агент/связь; NeedsAttention и сверка процессов/ресурсов до повтора или удаления |

Отмена прекращает новые действия и инициирует проверку незавершённого процесса. Удаление временной копии нельзя начинать, пока она используется загрузкой/SQL. Компенсация удаляет только ресурсы данной заявки. Исходный архив никогда не удаляется после успешного заказа, его отмены или ошибки.

## Критерии приёмки MVP
- Разработчик выбирает .dt с локального диска агента и получает работающую новую клиент-серверную базу.
- Разработчик выбирает .bak из UNC и получает новую базу без предварительной публикации шаблона.
- Оба сценария проходят без Git/EDT; исходные базы и файлы не изменяются.
- Несколько заказов из одного файла создают разные базы и соблюдают квоты.
- Замена файла между выбором и stage даёт ArchiveChanged, а не неожиданное содержимое базы.
- Недописанный файл, повреждённый .dt/.bak и неподдерживаемая упаковка не приводят к Ready.
- Агент может читать UNC, но SQL Server не может: выдача останавливается до RESTORE с понятной диагностикой.
- Доступные проекты, пути и конечные файловые объекты проверяются; выход из root и чужие архивы недоступны.
- При недостатке staging/SQL-места, отмене и потере агента остаётся отслеживаемое согласованное состояние.
- Старые пользовательские доступы и рабочие интеграции не активируются до и после выдачи тестовой копии.
- После успешной выдачи отображаются исходный архив, версия, этапы, срок и подключение.
