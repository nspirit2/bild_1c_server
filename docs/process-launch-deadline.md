# Optional monotonic launch deadline

Additive ProcessCommand.LaunchDeadline defaults null, preserving existing process behavior. ProcessLaunchDeadline carries a trusted TimeProvider, the timestamp captured BEFORE claim request and a positive budget <=5minutes. It is not authorization, a namespace hold or evidence of physical absence.

DemandNotExpired rejects negative elapsed or elapsed >= budget with fixed launch_deadline_expired, including trusted clock failure without raw diagnostics. Constructor rejects invalid_launch_deadline. It never uses local UTC or starts a new budget when the response arrives. Fixed ToString and deny System.Text.Json read/write including null prevent accidental persistence of an inherently in-process timestamp reference.

ProcessRunner checks cancellation again and then this guard after command validation, argv/environment preparation and Process construction, immediately before the existing Process.Start call. Deadline rejection is outside the start_failed catch, so it is distinguishable and no process start is attempted. No await lies between guard and launch. This narrows the setup-delay gap but cannot mathematically make checking and OS side effect atomic across arbitrary thread descheduling, clock jumps/rate anomalies or suspend behavior. It is a launch-entry guard, not automatic process cancellation at expiry and not a retry signal.

This increment does NOT yet propagate a creation claim through a real invocation adapter, does not enable a worker or CLI, and does not run RAC/CREATE. Future trusted composition must attach the SAME preclaim timestamp and server-derived remaining budget; inventing/restarting a deadline at invocation or delivery is forbidden. Normal runtime process timeout remains a separate bound after launch. Existing explicit cancellation/kill/drain semantics remain unchanged.
