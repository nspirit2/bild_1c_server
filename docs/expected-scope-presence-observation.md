# Caller-correlated paired presence observation

ObserveExpectedScopeAsync accepts a caller-created TargetPresenceAssessmentScope with fresh distinct RAC and SQL observation IDs. This is correlation, not proof of observation or authority. The named path always performs actual configured RAC then SQL observer reads, once each, and feeds both results into TargetPresenceAssessment.Assess for the EXACT expected scope. It never accepts a cached Boolean or promotes metadata to a claim.

All scope GUIDs, positive fencing token and distinct nonzero observation IDs are validated before either adapter can perform IO. Reservation-derived bs_test_* name is computed internally. RAC read carries expected canonical cluster and RAC mapping ID plus provided RAC observation ID; SQL read carries expected canonical SQL ID and SQL observation ID. Physical RAC argv mapping remains the explicit operator-bound observer configuration, not the canonical UUID.

The existing ObserveAsync(TargetPresenceRequest,credentials,ct) retains its API and generates new paired IDs itself before delegating to the same bounded sequential core. Existing total monotonic deadline and cancellation checks run before/between/after IO and assessment; observer exceptions stay fixed and redacted. Provider calls are cooperatively awaited, not detached on timeout. The path is read-only but will contact real targets if explicitly supplied real observers; tests use fake runner and fake DbConnection only.

This increment does not register a namespace/absence port or a creation host, wire a CLI/worker, acquire a claim or perform CREATE. Future trusted absence adapter must invoke this named method with coordinator-generated fresh IDs for each call and verify configured observation and creation physical pair compatibility. The namespace must remain held separately across both reads, claim and actual single invocation. Matching correlation alone is not a physical freshness fence.
